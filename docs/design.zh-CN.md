# 研究方案与实现范围

论文标题：**An Empirical Study of LLM Agents as Compilers for High-Performance Code Generation**。

研究比较三条路径：A 使用固定成熟编译器；B 让 LLM 从 C 生成并迭代汇编；C 让 LLM 生成并迭代一个共享编译器，再冻结该编译器处理新程序。C 不预设 IR 架构，也不能把源语言翻译委托给现有编译器。目标是测量正确性、目标程序性能、搜索成本及复用能力，不预设 LLM 已胜过传统编译器。

## 当前可以运行的部分

- Python 标准库实现的 CLI；Clang 原生编译和统一汇编/链接流程。
- A/B/C 三组执行流程。B 按程序轮流分配共享调用预算；C 每次修改同一个可复用 Python 编译器。
- 可配置 HTTP 模型接口、本地 JSON 命令、离线回放和明确标注的手写 smoke provider。
- 搜索、候选选择、最终测试三种输入流；开发与测试程序家族分离。
- 冻结清单及产物哈希检查；最终评估单独执行，不调用模型，也不把结果送回搜索。
- 边界/随机输入、参考编译器差分检查、输入修改检测、失败分类、进程超时。
- 自动计时批次校准、成对随机顺序测量、bootstrap 区间、完整分母报告。
- token/调用/墙钟时间账本、候选记录、回归与预算曲线、成本摊销的明确标注线性外推。

当前源语言范围是整数函数，ABI 为 `uint64_t kernel(const uint64_t *a, size_t n, uint64_t x)`。12 个自建 pilot 程序覆盖循环、分支、位操作、哈希、排序和小型库调用场景。4 个 smoke 程序用于离线验证流程。函数包装由传统编译器构建，不能把此轨道的结果称为完整应用编译器替代。

## 两条评估轨道

已知程序轨道：B 和 C 在相同开发程序集合上搜索，用独立最终输入比较性能。C 保持一个共享版本。B 的多个程序共用同一个总预算，不把每个程序的预算误当作总预算。

未见程序轨道：先在开发程序集上改进 C，再冻结编译器处理测试程序。B 可以对测试程序另开搜索，但计入逐程序成本。两者的在线工作不同，不能只用此轨道作因果归因。

搜索与候选选择均计入运行墙钟预算。token 上限按返回的实际用量控制，因此可能出现一次调用的超额；超额或用量未知的响应不会被选中。C 的起步失败同样是结果。正式实验需要多次独立 agent 运行，不能只重复二进制计时。

## 尚待扩展的研究部分

原讨论的 Embench、LLVM test-suite、TSVC、libc、ExeBench 和 Csmith 清单是候选方案，尚未完成逐项适配。对应工作与来源见 [benchmark 计划](benchmarks.md)。目前没有将自建样例冒充这批正式 benchmark，也没有运行付费 LLM 生成实验。

完整应用、多文件编译、浮点语义、可变数组输出、标准库实现对照、LTO/PGO、自包含可执行文件和更强等价性检查都需要后续轨道。库函数和完整应用分层报告；消除链接、缩小二进制、降低启动开销和提高计算速度是不同问题。

通过有限测试只表示通过该协议。bootstrap 区间反映当前运行内的计时噪声，不能证明语义等价，也不能替代跨 agent 运行、跨机器或多重比较分析。正式大规模实验需要固定模型版本、目标 CPU、预算、数据集版本、运行环境和排除规则后执行。
